## 场景与采样

- 日期：2026-09-11，北京时间（UTC+08:00）。
- 用户从 Web 前端选中三个 entry_exit 点发起 Replay。
- 未记录请求体，具体点 ID、点选/框选请求类型及返回点数不能由本记录确认。
- PostgreSQL 容器：`roadnet-dev-postgres-1`；Backend：`roadnet-dev-backend-1`。
- 采样区间：21:09:54.679 至 21:11:04.070；共享内存升高后回落稳定 15 秒自动停止。
- 每约 100 ms 采样；共 1,373 条，PostgreSQL 680 条、Backend 693 条；最大间隔分别 107 ms、101 ms。
- 容器内存读取 cgroup v2 `memory.current`，包含缓存等 cgroup 计费内存，不等于进程 RSS。
- PostgreSQL 共享内存读取 `/dev/shm` 文件系统已用空间，容量为 64 MiB。
- 原始采样：`/tmp/roadnet-memory-samples.jsonl`。该文件是临时运行数据，不提交 Git，可能被后续采样覆盖或系统清理。

## 请求结果与错误对齐

- 21:10:48.744：PostgreSQL 并行进程 PID 42230 报共享内存段扩容至 16,777,216 字节失败，`No space left on device`。
- 21:10:48.752：PID 41827 同样报共享内存扩容失败。
- 21:10:48.762 / .789：并行进程 PID 42230 / 42229 退出。
- 21:10:48.828：`POST /api/v1/map/replay` 返回 HTTP 503。
- 21:11:04：共享内存回落至约 1.03 MiB 并稳定，采样停止。

因此本次是失败请求基线，不是成功 Replay 的性能基线。采样峰值 51.62 MiB 低于 64 MiB 并不否定耗尽：采样存在时间间隔，且扩容申请可以在达到容量前失败。16 MiB 是报错中的目标段大小，不能简单视为额外新增 16 MiB。

## 解释范围

共享内存增长与 Replay 的 PostgreSQL 并行查询错误在时间上吻合，回落证明该占用是阶段性的。Backend 更早出现约 1.17 GiB 峰值；代码此前检查发现 Replay 会先全量获取 Clean 源数据并计算指纹，这与现象相符，但本次没有堆栈/堆内存剖析，不能将全部占用精确归因于该函数。

本次未修改共享内存容量、SQL 算法或数据库数据；后续优化应使用相同点 ID 和请求类型再比较。
