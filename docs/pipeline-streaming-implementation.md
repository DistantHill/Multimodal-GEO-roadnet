## 分工与提交规则

- 子代理按下方文件边界工作，不自行暂存或提交；主代理检查、测试并逐模块提交。
- 提交大小按新增与删除行数之和记录，2,000 行为软限制；文档与功能模块分别提交。
- 不使用全量暂存，不改动无关视觉工具迁移，不提交运行数据或凭证，不推送远端。
- 已交付第一批基础模块与生产读取修复，第二批交付账本、调度和暂存基础及组合验证。后续任务按依赖推进，
  基础模块完成不等于 Clean/Detect 可恢复已接通，更不等于 26M 性能目标已达标。
- 每个代码模块有定向测试；集成运行 `make test`，前端涉及测试时运行 `npm test`。
  真实数据库/26M/内存限制验收单独记录，不能用模拟测试代替。

### P01：生产指纹读取

保持已有引用源行集合、排序、摘要版本和返回字段不变，仅消除客户端全量结果缓冲。
游标名称唯一，读取批量正整数校验，异常必关闭，不自行提交/回滚调用方事务。
该摘要目前只覆盖 Clean 输出引用的行，不冒充完整封存输入指纹。

### P02：任务清单与子轨迹规划

对组元数据而非全部原始行装箱；末组使当前任务超 n 时整体留给下一任务，单组
超过 n 则独占。调用方按 `SubtrackGroup.order_key` 提供严格递增组序列：先运行标识，
再键类型及键值；整数键按数值排序，字符串键按字典序，数值子轨迹索引不得转成字符串。
模块不全量排序，遇重复或乱序立即拒绝；后续读取器须显式满足该前置条件。固定清单身份不包含
n/W/T/机器信息；未知配置默认影响语义，执行配置仅通过明确白名单排除。
此模块首批不接生产调度，不声称已实现持久完成账本。

### P03：预算与环境记录

按调用方实测基线、单进程开销、每行峰值估算及缓冲/安全余量推导执行参数；
记录假设和预算分解。采集 CPU、可用配额、内存与磁盘环境，未知项明确标记。
不通过估算冒充物理内存硬限制，不在测试中修改控制组或运行磁盘压力测试。

### Clean 接入前已查明的条件

1. 新 `calculate_input_fingerprint` 覆盖全部源行的 `id/vehicle_id/timestamp/lon/lat/heading/speed/extra`
   规范编码，区分 SQL 空车辆标识与字符串 `"None"`，版本与旧引用摘要分离；不覆盖任意
   自定义列或 `geom`，也不提供封存。现有解析器可能优先消费 `vid/lng/gps_time_a` 等别名，
   新恢复入口必须先固定规范列投影/映射或拒绝冲突，不能直接把新摘要用于任意 `SELECT *`。
2. `clean_vehicle` 仍接收完整车辆列表，并按完整分段数决定车辆子轨迹命名；解析器还会跳过
   无效行。分组规划必须保持这些语义，不按原始行数机械切割。
3. 现有 `pipeline.py` 从 1 累加全局 `subtrack_index`，写入层按偏移重编号；并行落库不能按
   计算完成顺序分配。必须持久规划稳定编号/映射，并核对外键、引用字段和恢复身份。

上述条件明确了下一批范围，不是已完成 Clean 业务恢复。空间父子拆分与归并、超大组外存
路径、完整链路差分和 26M 容量验收仍未完成。

| Replay 请求 | 来源键、resolved ID、交叉口三选一；resolved ID 必带 `detect_id`；拒绝 bbox | 来源键转字符串，携带运行/数据库上下文 | 用合法 UUID 字符串验证运行 ID，不只用数字假数据 |
| Clip 请求 | `detect_id`、两个不同正整数 `intersection_ids` | 恰好选择两个交叉口 | 保持字段一致；服务器负责最终验证 |
| 错误响应 | HTTP 错误 `detail` 可含 `error/message/sqlstate` | 显示 `detail.message` 等错误内容 | 不吞掉资源错误，不暴露 SQL/凭证 |

来源：`apps/backend/src/backend/map_api.py` 的 `run_catalog`、`read_layer`、各
`_..._feature` 与 `_feature_collection`；`map_schemas.py` 的请求模型；
`apps/frontend/src/map-api.js` 的请求/标准化函数；`main.js` 的 `syncRuns`、
`decorateFeature`、`refreshRuns`。本批不改变这些公开字段；迁移后仍需重新联调。
