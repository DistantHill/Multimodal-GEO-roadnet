依据：[已确认规格说明（specification，Spec）](pipeline-20m-memory-budget-spec.md)第 9 节。
术语遵循[项目术语与写作规范](terminology.md)，本文件只记录执行，不另建同主题设计。

授权日期：2026-09-13。用户要求子代理分步实施、按小模块提交，尽量不超过 2,000 行。

## 分工与提交规则

- 子代理按下方文件边界工作，不自行暂存或提交；主代理检查、测试并逐模块提交。
- 提交大小按新增与删除行数之和记录，2,000 行为软限制；文档与功能模块分别提交。
- 不使用全量暂存，不改动无关视觉工具迁移，不提交运行数据或凭证，不推送远端。
- 已交付第一批基础模块与生产读取修复，第二批交付账本、调度和暂存基础及组合验证。后续任务按依赖推进，
  基础模块完成不等于 Clean/Detect 可恢复已接通，更不等于 26M 性能目标已达标。
- 每个代码模块有定向测试；集成运行 `make test`，前端涉及测试时运行 `npm test`。
  真实数据库/26M/内存限制验收单独记录，不能用模拟测试代替。

### P01：生产指纹读取

保持已有引用源行集合、排序、摘要版本和返回字段不变，仅消除客户端全量结果缓冲。
游标名称唯一，读取批量正整数校验，异常必关闭，不自行提交/回滚调用方事务。
该摘要目前只覆盖 Clean 输出引用的行，不冒充完整封存输入指纹。

### P02：任务清单与子轨迹规划

对组元数据而非全部原始行装箱；末组使当前任务超 n 时整体留给下一任务，单组
超过 n 则独占。调用方按 `SubtrackGroup.order_key` 提供严格递增组序列：先运行标识，
再键类型及键值；整数键按数值排序，字符串键按字典序，数值子轨迹索引不得转成字符串。
模块不全量排序，遇重复或乱序立即拒绝；后续读取器须显式满足该前置条件。固定清单身份不包含
n/W/T/机器信息；未知配置默认影响语义，执行配置仅通过明确白名单排除。
此模块首批不接生产调度，不声称已实现持久完成账本。

### P03：预算与环境记录

按调用方实测基线、单进程开销、每行峰值估算及缓冲/安全余量推导执行参数；
记录假设和预算分解。采集 CPU、可用配额、内存与磁盘环境，未知项明确标记。
不通过估算冒充物理内存硬限制，不在测试中修改控制组或运行磁盘压力测试。

- 最终 `make test`：后端 74 通过，Pipeline/视觉工具 762 通过、22 跳过。
  新增账本/组合数据库测试默认跳过 18 项，已在真实 PostgreSQL 单独补验。

  账本测试使用自身新建的随机结构，结束后删除该测试结构；指纹仅使用临时表。
  清理的是可重建测试数据，未安装生产账本、修改业务表或删除业务数据。
- 已验证：不同连接/阶段的运行排他、事务内部分结果对观察连接不可见、回调失败
  全部回滚、重复交付不重复生效、固定清单有界恢复、旧代次/尝试拒绝、跨重启三次
  上限、持久退避、封闭清单后发布，以及真实进程池→暂存文件→中央事务的组合。
- 故障注入在真实数据库完成提交后丢弃确认，重连查询完成记录避免重算；另在获取锁
  后丢弃确认，验证连接关闭释放锁，不阻塞新协调器。并未声称覆盖全部断电/网络故障。
- 交叉审查发现并修复三项问题：包初始化提前加载 NumPy；子进程异常对象及堆栈
  无界传输；获取锁确认丢失时会话锁残留。已分别补数值库导入时序、巨大不可序列化
  异常和锁确认丢失回归。子进程失败仅返回有界类型/类别，不传原消息及堆栈。

### 后续接入顺序与限制

1. 完成 P05 的中央资源预留、预算与实际运行记录接线、持久失败分类和恢复派发；
   当前进程池不自行重试，账本负责计数/退避，但两者还没有生产协调入口。
2. 接入 P06 的完整源输入指纹、Clean 业务读取/写入及正式阶段发布。账本的
   `publish()` 只发布账本阶段，不会自动更新 `clean_runs` 或 `detect_runs`。
3. 在 Detect 接入前实现父子拆分和必要归并。当前 `parent_id` 非空明确拒绝；
   永久/资源故障或三次耗尽后的人工重开仍待实现，不以新任务身份绕过尝试上限。

写入回调是受信任的同步事务代码，只能用提供的游标写业务结果，不得自行执行事务控制、
解锁或外部副作用。暂存读取必须在事务内成功耗尽并校验后才能提交。已发布文件不自动
回收，全局磁盘额度、残留尝试目录和恢复依赖的回收需中央协调器统一管理。
进程池取消尚未启动的任务，已运行任务关闭时可能等待；当前没有强杀/超时恢复能力。
线程变量在子进程数值内核加载前设置，但实际启动入口也必须避免提前导入数值库。
