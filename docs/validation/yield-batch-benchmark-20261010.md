# Pipeline 批次大小基准测试 20261010

本轮已验证候选中，共享批次（batch）设置建议为
`runtime.relation_batch_size=32768`、`detect.stream_batch_size=4096`，
Cross 线段对批次保持 65536。配置尚未修改。

## 数据来源与测量范围

实验由 GPT-6.1 Sol、low 推理设置的子代理执行。独立进程限制为 2 核中央处理器
（CPU）、4 GiB 内存上限，禁用交换空间。使用启动时冻结的源码和配置，源码摘要为
`3a18520b6daeda96e69469bcd1c106c01577fb6b5d11914e1a25e3078b267cb0`。
基准配置来自 /data/workspace/Multimodal-GEO-roadnet/services/pipeline/config/pipeline.toml ，
仅运行指定阶段的基准测试，没有启动 Pipeline 冒烟测试或全量测试。

Clip、Fitting 和转向事件（turn events）的真实样本来自 Refine
`10d26050-d9f8-4f6f-adf8-f59776485ac9`、Detect
`9f79758c-5a04-4d73-ad6b-2db11cff8a61`。片段共有 72,834 条、900,572 个几何点，
其中交叉口之间的片段为 24,783 条；转向事件为 97,043 条。
Topology 使用 55 个交叉口窗口子集，累计读取 2,245,663 个点出现次数，同一点可出现多次。

Cross 使用另一份历史 Refine `f76bab1e-1af1-45d0-9368-cc2a67aceb04`
的 `(0, 0)` 网格，共 111,647 条线段，平均速度阈值为 5.0，产生 1,212,060 条候选。
正式中间关系测试保留生产者原有的 35 个输入批次边界。
外存溢写（spill）诊断只取规范顺序的前 32,768 条线段并强制溢写；完整样本实际走内存路径。

## 推荐值与实测结果

以下耗时为各组至少三次测量的中位数，排除预热。

| 参数或阶段 | 对照设置 | 耗时 | 结论 |
| --- | --- | --- | --- |
| Cross 正式中间关系 | relation 1024 / 16384 / 32768 | 43.38 / 25.14 / 25.26 s | 16384 单阶段最快；共享设置采用 32768 |
| Clip 构建与 Fitting 首轮矩阵 | relation 1024 / 16384 | 59.15 / 47.84 s | 1024 偏小，耗时减少 19.1% |
| Clip 构建与 Fitting 最终配对 | relation 16384 / 32768 | 48.91 / 47.94 s | 32768 再减少 2.0%；反转执行顺序的单次对照仍更快 |
| Turn 与 Topology 独立中位数之和 | relation 32768，stream 1000 / 4096 / 8192 | 27.10 / 26.22 / 26.48 s | 共享 stream 采用 4096 |
| Cross 内存计算路径 | pair 16384 / 65536 / 131072 | 3.85 / 3.62 / 3.64 s | 保持 65536；131072 未改善耗时且驻留内存更高 |
| 强制溢写子集 | block 4096 / 8192，pair 65536 | 37.22 / 33.70 s | 8192 是已重复验证的诊断最优值；当前生产样本不触发此路径 |

relation 在 Turn、Cross 中按关系行计量，在 Clip 中还限制每个读取批次的点数；
单个超长片段可超过该点数预算。Cross pair 的当前配置键是
`detect.candidate.cross.params.default.cross_track_pair_batch_size`，
冻结配置中的旧键是 `detect.cross_track_pair_batch_size`。
`runtime.db_stream_batch_size=2000` 当前仅声明、校验，没有运行时消费者。

共享设置通过比较 relation 的 16384、32768 与 stream 的 1000、4096、8192 六种组合选择，
目标为 Clip/Fitting、Cross 中间关系、Turn、Topology 各自中位耗时之和。
这是不同阶段样本的比较目标，不能作为完整 Pipeline 墙钟耗时或全局最优值。
强制溢写 block=16384 的单次试跑更快，但未重复测量和验证全字段，不据此修改生产默认值。

## Fitting 重复读取的原因与优化方向

Fitting 累计重建 301,151 条片段，相对于 72,834 条输入片段为 4.1348 倍。
计数只覆盖 Fitting，已扣除测试驱动程序此前的完整正确性遍历。
该数字是平均读取放大，不表示每条片段都恰好解码四次，也不表示拟合结果重复。

`fit_centerline_variants()` 分别拟合合并、正向、反向三个变体，每个变体先完整遍历
72,834 条片段，再判断类型和方向。这三次准备遍历合计重建 218,502 条片段。
边界片段共有 48,051 条，它们每轮也先读取几何再被过滤。
随后 `_fit_pair_stream()` 先读取交叉口对的片段统计长度，再为每个采样分块重新读取；
累计 857 次 `iter_pair()` 调用，重建另 82,649 条片段。
两部分相加正好为 301,151。

每次读取都查询点关系、逐点填充数组并构造 `TrackClip`。增大 relation batch
能减少点批次查询次数，不能减少上述片段重建总量。
基线单次试跑中，点批次读取及对象重建占 Fitting 耗时约 63.6%；
该比例包含查询和读取工作，不是纯解码占比，也不能直接推算优化后的提速比例。

可实施的优化是共享三个变体的片段筛选、校验和长度统计，并在读取几何之前过滤类型、方向；
随后按交叉口对复用已解码的几何与累计弧长。三个变体的采样位置可能不同，
仍需分别采样和聚合。几何复用应限定内存预算，超大交叉口对保留分块读取或磁盘暂存，
不能把现有 16 MiB 采样块预算误当作新增几何缓存的预算。
有效片段判定、异常报告顺序、来源标识符顺序和三个变体的结果需保持一致。
本报告所记批量实验只定位了问题，未实施此优化。后续设计已确定超限时复用原 DuckDB
关系，不新增自写磁盘暂存；两步实现与验收已完成，见
 [fitting-read-reuse-20261010.md](fitting-read-reuse-20261010.md) 。

后续两步实施计划、仓库约束与验证矩阵见
 [/data/workspace/Multimodal-GEO-roadnet/docs/fitting-read-reuse-plan.md](/data/workspace/Multimodal-GEO-roadnet/docs/fitting-read-reuse-plan.md) 。
